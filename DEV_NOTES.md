## 📁 Архітектура проєкту

- **`src/assets/`** — Статика: картинки, іконки (`.png`, `.svg`), шрифти.
- **`src/components/ui/`** — "Тупі" UI-компоненти. Універсальні, не прив'язані до бізнес-логіки (кнопки, інпути, модалки, спінери). Вони отримують дані лише через `props`.
- **`src/components/features/`** — "Розумні" предметні компоненти. Прив'язані до логіки проєкту (картка картини, форма оформлення замовлення, список товарів кошика). Можуть самі тягнути дані зі стору.
- **`src/components/modals/`** — Спливаючі вікна: головний блок для їхнього показу (GlobalModal) та форми, які з'являються всередині (ContactUsForm).
- **`src/components/layout/`** — Каркасні компоненти (Header, Footer, Sidebar, Layout-обгортки).
- **`src/hooks/`** — Кастомні React-хуки (`useDebounce`, `useOnClickOutside`).
- **`src/pages/`** — Компоненти сторінок, які підключаються безпосередньо в Router (`HomePage.tsx`, `CatalogPage.tsx`).
- **`src/services/`** — API-клієнти, запити на бекенд (екземпляр `axios`, файли з ендпоінтами).
- **`src/store/`** — Глобальний стейт (`Zustand`).
- **`src/types/`** — Спільні TypeScript-інтерфейси (моделі `Artwork`, `User`, `CartItem`), щоб не дублювати їх по компонентах.
- **`src/utils/`** — Допоміжні функції-хелпери (форматування ціни, дати, утиліта `cn`).

## 🔗 Деталізація вкладених маршрутів (Nested Routes)

Особистий кабінет (`/profile`) та адмін-панель (`/admin`) використовують вкладений роутинг.

**Гілка `/profile`:**
- `/profile` — Базові налаштування (редагування даних) та список "Вибране".
- `/profile/become-artist` — Форма подачі заявки на художника (тільки для ролі `user`).
- `/profile/my-artworks` — Управління своїми картинами (тільки для ролі `artist`).
- `/profile/add-artwork` — Форма додавання нової роботи (тільки для ролі `artist`).

**Гілка `/admin`:**
- `/admin` — Дашборд із загальною статистикою.
- `/admin/artists` — Модерація нових авторів (схвалення заявок).
- `/admin/artworks` — Модерація нових картин перед публікацією в галерею.

## 📱 Стратегія адаптивного дизайну (Responsive Web Design)

Проєкт використовує підхід **Mobile-First** та Fluid Design.
Базові Tailwind-класи пишуться для мобільних пристроїв. Для адаптації під більші екрани використовуються стандартні брейкпоінти Tailwind:

- **Базові класи (без префікса)** — Мобільні пристрої (< 768px). Еталонний макет: 393px.
- **`md:` (від 768px)** — Планшети. Перебудова сіток, збільшення шрифтів.
- **`lg:` (від 1024px)** — Ноутбуки та десктопи. Відновлення горизонтальних меню, складних Grid-структур. Еталонний макет: 1440px.
- **`xl:` (від 1280px)** — Великі монітори (використовується рідко, для обмеження максимальної ширини контейнерів).

**Глобальні відступи:** Класи `px-global` та `pt-header` автоматично змінюють свої значення залежно від розміру екрана завдяки CSS-змінним у `index.css`.

## 🎨 Анімації головної сторінки (Hero Section)

- **Перший рендер (перший візит або оновлення сторінки):**
  Анімації відбуваються каскадом. Спочатку плавно з'являється `HeroLogo` (шляхом fade-in), потім проявляється `HeroFrame`, і насамкінець плавно виїжджає `HeroSlider` зі своїми елементами керування. Стан першого завантаження фіксується в глобальному сторі (Zustand).

- **Повторний рендер (повернення на головну з іншої сторінки):**
  Усі тривалі вступні анімації пропускаються. `HeroFrame` та `HeroSlider` відразу відображаються на своїх місцях. Замість базового fade-in спрацьовує shared layout анімація (`framer-motion`): маленьке `Logo` з хедера плавно перелітає та трансформується у велике `HeroLogo` по центру екрана з ефектом пружини.

## 🖼️ Логіка роботи галереї (Фільтрація, Сортування, Пагінація)

Галерея побудована за концепцією **Single Source of Truth** (єдине джерело правди), яким виступає глобальний стор Zustand (`useArtworkStore`). Стан фільтрів не розкиданий по локальних компонентах, що запобігає розсинхронізації між UI та API.

**Сувора типізація та Константи:**
Уся логіка спирається на файли констант (`galleryConstants.ts`) та загальні типи (`types/artwork.ts`). Фронтенд використовує ті самі типи значень (наприклад, `ArtworkCategory`, `ArtworkSort`), що й бекенд.
*   **Як додати нове значення/фільтр у майбутньому:**
1) Додати значення у відповідний Union-тип (бек-енд модель);
2) Оновити список опцій у `galleryConstants.ts`;
3) Переконатися, що утиліта-мапер `formatGalleryParams` правильно обробляє нове поле;
4) Додати чекбокс/кнопку в UI.

**Покроковий життєвий цикл (Data Flow) при роботі з фільтрами:**
1. **Взаємодія (Клік):** Користувач відмічає категорію, змінює ціну або обирає сортування.
2. **Оновлення Store:** Компонент викликає дію (`setFilters` або `setSort`) та зберігає нові параметри в Zustand.
3. **Реакція (Синхронізація):** `useEffect` у `GalleryPage` помічає зміну. Він миттєво скидає скрол сторінки вгору та встановлює `page = 1` (щоб почати пошук з першої сторінки).
4. **Трансформація (Мапер):** Перед запитом викликається хелпер `formatGalleryParams`. Він перетворює зручний для UI стан (масиви, як-от `['oil', 'acrylic']`) у формат, який чекає сервер (рядок `'oil,acrylic'`). *Розумний дефолт:* якщо зняти всі статуси (AVAILABLE/SOLD), мапер сам підставить усі можливі статуси, щоб завантажити весь каталог.
5. **Запит до API:** Стор викликає `fetchGalleryArtworks` із параметром `append = false`. Старий масив картин очищається і перезаписується новою відповіддю від сервера.
6. **Рендер Сітки:** `ArtworkGrid` отримує нові дані. Важливо: грід розподіляє картини по колонках (Masonry), але **не сортує їх локально**, довіряючи тому порядку, який повернув сервер.

**Пагінація (Кнопка "See More"):**
Працює за тим самим алгоритмом, але замість скидання сторінки на `1`, вона інкрементує поточну сторінку (`meta.page + 1`) і передає в `fetchGalleryArtworks` прапорець `append = true`. Це дозволяє додавати нову порцію картин у кінець існуючого масиву, не ламаючи розраховану сітку.
